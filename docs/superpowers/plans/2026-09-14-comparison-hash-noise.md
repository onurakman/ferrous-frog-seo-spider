# Comparison Hash Noise

**Problem:** Saved-session SQL and archive comparison classify any unequal raw response hashes as Changed. Dynamic HTML attributes or scripts can therefore make unchanged captured text and SEO fields appear changed. This explains a possible trigger; the user's actual site has not been reproduced.

**Design:** Preserve the existing response-byte hash and exact-duplicate rules. Persist an exact fingerprint of the parser's normalized captured text with a version, raw/rendered source and content-selector context; complete non-HTML responses use a versioned byte fingerprint. Missing or incompatible captures remain explicitly unavailable. Compare existing SEO fields plus heading/count, canonical/count and robots evidence. Raw-only differences get separate complete counts and an opt-in server-side row filter, applied before the existing detail cap. Expose reasons and metadata values in the current dialog.

**Scope:** Reuse existing parsing, storage migrations, SQL comparison, archive serialization and UI request guards. No new packages (the existing workspace serde_json dependency is now available in the engine runtime), raw HTML retention, broad dynamic-content heuristics, full comparison workspace or identity-policy change. Content selectors can exclude known volatile visible regions; no universal timestamp/token stripping. Comparison text retains the existing parser’s text-node whitespace policy and does not compute CSS visibility.
